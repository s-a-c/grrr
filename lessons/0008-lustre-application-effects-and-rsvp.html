1. React useEffect vs. Lustre Managed Effect(Msg)

In Lesson 0007, lustre.simple kept init and update purely in memory. To talk to Glimr's HTTP API without breaking purity, lustre.application(init, update, view) changes their return types to a tuple: #(Model, Effect(Msg)).

React (useEffect + fetch)

useEffect(() => {
  let cancelled = false;
  fetch("/api/grrrs")
    .then(r => r.json())
    .then(d => { if (!cancelled) setGrrrs(d.grrrs); });
  return () => { cancelled = true; };
}, []); // dependency arrays, races, try/catch...

Side effects run imperatively inside component lifecycles with manual cancellation and unvalidated JSON.

Lustre (application + rsvp)

fn init(_flags) -> #(Model, Effect(Msg)) {
  #(Model(..initial, loading: True), fetch_grrrs())
}

fn fetch_grrrs() -> Effect(Msg) {
  let dec = decode.field("grrrs", decode.list(grrr_decoder()), decode.success)
  rsvp.get("/api/grrrs", rsvp.expect_json(dec, GrrrsFetched))
}

init and update stay 100% pure — they return data describing the HTTP effect, and Lustre dispatches the decoded Msg.

#(Model, Effect(Msg))

Pure transitions: update never calls fetch() directly; pure branches like AuthorChanged return #(model, effect.none()).

rsvp.expect_json

3-step guard: Checks 2xx status, application/json header, and runs your decode.Decoder before wrapping into Result.

/api Dev Proxy

Zero CORS: Adding [tools.lustre.dev] proxy in client/gleam.toml forwards /api from port 1234 to Glimr on 8000.

Key Guarantees in client.gleam

  • Duplicate-submit guard: Model.submitting disables the submit button and makes Submitted ignore repeat clicks while POST /api/grrrs is in flight.
  • 0ms local pre-validation: Submitted runs shared/post.new_draft_all before dispatching post_grrr(draft), catching bad handles/bodies without an HTTP round-trip.

fn post_grrr(draft: DraftGrrr) -> Effect(Msg) {
  let payload =
    json.object([
      #("author", json.string(handle.to_string(draft.author))),
      #("body", json.string(post.to_string(draft.body))),
    ])
  let decoder = decode.field("grrr", grrr_decoder(), decode.success)
  rsvp.post("/api/grrrs", payload, rsvp.expect_json(decoder, GrrrPosted))
}

fn grrr_decoder() -> decode.Decoder(PostedGrrr) {
  use id <- decode.field("id", decode.string)
  use author <- decode.field("author_handle", decode.string)
  use body <- decode.field("body", decode.string)
  use created_at <- decode.field("created_at", decode.string)
  decode.success(PostedGrrr(id:, author:, body:, created_at:))
}

In-Depth: rsvp.expect_json vs. Parsing 422 Field Errors

rsvp.expect_json checks for a 2xx status first: any 4xx or 5xx response becomes Error(rsvp.HttpError(resp)) where resp is the full Response(String). Because shared/post.new_draft_all already caught handle and body validation errors before sending the request, 422 rarely triggers from the SPA — and if you later want to parse server-side 422 field errors (such as uniqueness or rate-limit rules), you can swap in rsvp.expect_any_response and branch on resp.status directly.
