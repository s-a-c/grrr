1. Managed Effect(Msg) vs. React useEffect

In Lesson 0007, lustre.simple kept init and update purely in memory. To talk to Glimr's HTTP API without breaking purity, lustre.application(init, update, view) changes their return types to a tuple: #(Model, Effect(Msg)).

update Stays Pure

vs. React: No useEffect dependency arrays or stale closures.

update never calls fetch() directly — it returns a description of the HTTP request (Effect(Msg)), and Lustre's runtime executes it and feeds the result back as a Msg.

rsvp + gleam_json

vs. Axios / fetch: Typed responses decoded at the edge.

rsvp.get and rsvp.post build Effect(Msg) values. Paired with rsvp.expect_json(decoder, Msg), Lustre only delivers your data after status 2xx, application/json content-type, and JSON decoding all pass.

Dev Proxy (/api)

vs. Vite proxy: Same-origin URLs in dev and prod.

Adding [tools.lustre.dev] proxy = { from = "/api", to = "http://localhost:8000/api" } to client/gleam.toml lets lustre/dev forward /api/* to Glimr with zero CORS headers needed.

How lustre.application Differs from lustre.simple

  • Tuple return: Both init(flags) -> #(Model, Effect(Msg)) and update(model, msg) -> #(Model, Effect(Msg)) return a new model paired with an effect.
  • No-op branches use effect.none(): Pure UI updates like AuthorChanged or BodyChanged return #(updated_model, effect.none()).
  • Optimistic UI guard: Keeping submitting: Bool in Model lets Submitted disable the submit button and ignore duplicate submits while the POST /api/grrrs effect is in flight.

    fn fetch_grrrs() -> Effect(Msg) {
  let decoder = decode.field("grrrs", decode.list(grrr_decoder()), decode.success)
  rsvp.get("/api/grrrs", rsvp.expect_json(decoder, GrrrsFetched))
}

fn post_grrr(draft: DraftGrrr) -> Effect(Msg) {
  let payload =
    json.object([
      #("author", json.string(handle.to_string(draft.author))),
      #("body", json.string(post.to_string(draft.body))),
    ])
  let decoder = decode.field("grrr", grrr_decoder(), decode.success)
  rsvp.post("/api/grrrs", payload, rsvp.expect_json(decoder, GrrrPosted))
}

fn grrr_decoder() -> decode.Decoder(PostedGrrr) {
  use id <- decode.field("id", decode.string)
  use author <- decode.field("author_handle", decode.string)
  use body <- decode.field("body", decode.string)
  use created_at <- decode.field("created_at", decode.string)
  decode.success(PostedGrrr(id:, author:, body:, created_at:))
}

In-Depth: rsvp.expect_json vs. Parsing 422 Field Errors

Notice how rsvp.expect_json checks for a 2xx status first: any 4xx or 5xx response becomes Error(rsvp.HttpError(resp)) where resp is the full Response(String). Because shared/post.new_draft_all already caught handle and body validation errors before sending the request, 422 rarely triggers from the SPA — and if you later want to parse server-side 422 field errors (such as uniqueness or rate-limit rules), you can swap in rsvp.expect_any_response and inspect resp.status directly.
